# 阶段 1：立项（调研 + 初设 + 总框架）——6 阶段定稿版

> 状态：**已定稿 V2.8**（2026-08-20；变更记录见文末）
> 上游接口：用户想法 / 业务方需求（本阶段入口，无文档依赖）
> 下游接口：向阶段 2 输出总框架（PRD 定稿、契约骨架、评测基线）与《技术方案书》（选型决策、PoC 结论）

---

## 一、阶段定位

**用户原话要旨**：立项 = 原来的立项 + 初设 + 总框架等——调研、初步设计、总框架一条线走完，为施工图设计（阶段 2）备齐"双明确"前提。

一句话：**把"要做什么"（需求）和"用什么方法做"（方案）都钉死，并立好总框架宪法。**

## 二、融合后完整流程

### 步骤 0：先查后造
检索现成方案：开源项目、现成工具/API、公司既有资产、知识库历史案例（含上次复盘沉淀）。查过什么、为什么不用，一句话记录。

### 步骤 1：目标确认卡（含止损线）
六要素全部可判定：**本质核心 = 用户需求因果链（第 0 要素，V2.7 升级）**——链上八问逐条答清：①谁需求 ②需求什么 ③为什么需求 ④可如何解决 ⑤解决方式是否是用户希望的方式 ⑥是否最好的方式 ⑦是否简单易操作 ⑧结果是否可靠；**链上答不全，不立项**（V2.5「凭什么被需要」表述（V2.7 替换）：那是从"我"的角度自我辩护，不是用户视角的根据——需求就对应使用，需求就是用户）；**用户定稿链路总览（V2.8）**：需求链八问（谁需要/需要什么/为什么需要/如何解决需要）→ 设计（能用/好用/想用）→ 验收（是否能用/是否好用/是否想用）→ 交付（用户亲手走一遍）→ 复盘（下个项目修正）；核心全文在《立项报告》第一节、PRD 文首、进度总览顶部**常驻**，每会话开工必读，防过程杂事干扰遗忘 / **真实目标**（解决 XX 场景 YY 问题达到 ZZ 效果）/ **完成标准**（可测量：准确率、成本、效率 + **核心验收指标**——核心验收必须用户亲验，AI 不得代判代签）/ **范围边界**（做什么 + **不做什么**）/ **关键约束**（预算、时间、合规、算力）。
- **止损线**：最大投入金额 + 最大投入时间 + **触发后做什么**（转 API 方案 / 砍功能 / 暂停）——只定线不定义动作，线就是摆设。
- **成本口径统一定义（V2.2）**：成本 = API 调用费 + 算力（GPU/云）+ 人力折时，三列分记——止损线（本阶段）、燃尽项（阶段 3）、增量压测（阶段 4）、全链路压测（阶段 5）按**同一口径**记账，才能对账。
- **澄清前置**：含糊处当场问清（给 2~4 选项 + 各自影响），不把歧义带进后续文档。
- 用户确认后才进入下一步。
- **代行边界（V2.6，2026-08-20 中华神文实证）**：用户明确预先授权代行时（如离场指令「换做我来思考」），导师可以「代拟稿」推进至核心验收闸前——代拟内容逐项标注、用户亲签前为工作假设；**核心验收（用户亲验）不豁免**，项目必须在闸门停下等待。
- **术语链（V2.5 补）**：本质核心（一句话命题）→ 拆成可验证的**核心假设**（PoC 对象）→ 验过后固化为**核心验收指标**（进 PRD 验收标准）。

### 步骤 2：数据资产盘点
按盘点表执行：数据源、类型、量、质量（1-5）、标注、更新频率、获取难度、合规风险。

### 步骤 3：技术路线比选（前期决策优先）
给 **2~3 个候选方案**（直接 API / 微调 / RAG / 自研 / 现成开源），对比维度：成本、效果、周期、可控性；写利弊与推荐项，**用户拍板**，决策记录留档（后续换路线 = 关键变更，走变更单）。

### 步骤 4：PoC = 最小验证
- 先问：本项目**最险/最没把握的一段**是什么？
- **选段排序（2026-08-20 新增，中华神文教训）**：核心假设（核心价值成立吗——好不好玩/准不准/有没有人看）**永远是第一候选最险段**，技术可行性排后。游戏的 PoC 不是「引擎能不能跑」，是「核心玩法原型好不好玩」；股票软件的 PoC 不是「数据能不能采」，是「规律预判准不准」。
- 只验证这一段，end-to-end 跑通 1 个案例即可，不全面铺开；
- **判定标准（V2.2）**：PoC 结论必须回答"最险点对应的指标是否达到立项目标的最低线"（如检索准确率 ≥70%）——"跑通 1 个案例"只是必要条件，**指标达标才算成立**；**成立** → 写《PoC 验证报告》进下一步；**不成立** → 立即停下，说明"错在哪、代价、怎么退回"（回步骤 1/3），不带着风险进详细设计。
- **阈值可行性预检（V2.6）**：代理指标（如「中位数 ≥N」）定稿前，先做小规模规则空间扫描证明可达；做不到就标「暂定」待 PoC 实测校准——禁止拍脑袋定阈值（中华神文 M2「≥20」与 MAX_ACTIONS=20 同源撞车实证）。

### 步骤 5：规模预判（拆分组装法启用判定，V2.2 明确口径）
触发判据（满足任一即启用）：
- **主判据（立项时可操作）**：功能模块数 >3 或预计子代理 ≥4——直接数得出来；
- **校准判据（事后校准）**：单会话累计上下文超 **20 万 tokens**（成本机制，与上下文长度无关）——用同类历史项目实测数据回填参考；本项目实测值记入阶段 6 复盘校准。
- 判定结果写入立项报告；按总览「三档裁剪」选择执行档位。
- **量化基准冷启动（V2.3）**：首次项目无实测数据时用初始参考区间——单任务包 0.5~2 人天、瑕疵率 3%~8%（按项目类型：RAG 类偏下、生成类偏中、Agent 类偏上）；实测值由阶段 6 复盘回填修正。

### 步骤 6：总框架（宪法）
1. **《产品需求文档-PRD》定稿**：F1/F2…逐条**需求链式条目**（V2.7）——每条含「①用户使用层：作为[谁]/在[什么情境]/想[达成什么]」+「②系统响应层：系统应当[如何响应]」；需求链④⑤⑥⑦⑧映射列（解法/用户希望/最优/易操作/可靠）；不做的范围、验收标准（含使用层结果：用户做成事 + 功能指标）、变更记录表（初始空）；任何会话对需求有冲突，以 PRD 为准。
2. **契约骨架**：模块边界与数据流图、全局 schema 框架、模块间 API 签名框架、统一 id 前缀、**契约冻结规则**（改契约先停下报告→用户确认→升版；**分级细则见 03 §步骤 7**：①级向后兼容新增子条目免确认）。任务包级细化留给阶段 3。
3. **评测基线冻结**：P0/P1/P2 指标体系、核心评测集基线版本、通过阈值（P0 必须 100%）、Badcase 定义标准（什么算错、谁判定）。
   - 评测集构建口径（V2.2）：ground truth 来源、用例量级下限（P0 用例 ≥ 核心场景最小集）、标注成本预算——冻结时一并记录，防 Goodhart 风险从评测集侧转移到构建侧。

### 步骤 7：类比讨论定调（V2.7 新增，进详细设计前最后一道闸）
需求链八问答清、总框架定稿后、进 02 之前：
1. **先查后造**：检索类似项目（同类工具/竞品/开源/公司历史项目/知识库案例），列 2~3 个候选参照；
2. **类比讨论**：逐个讲清「人家怎么解决、用户怎么接受、我们借鉴什么、避开什么坑」；
3. **定调**：用户拍板解决方式的最终形态（关键决策留档）——**才允许进入 02 详细设计**。
> 类比是防「闭门造车」的最后一道闸；定调后若同类项目出现更优方案，按变更通道处理。

## 三、检查清单

- [ ] **用户需求因果链八问答清 + 用户已确认**（《立项报告》第一节、PRD 文首、进度总览顶部常驻，V2.7 升级）
- [ ] **类比讨论定调完成**（2~3 候选类比、用户拍板解决方式最终形态）
- [ ] 目标确认卡六要素齐全 + 用户已确认（含澄清前置；完成标准含核心验收指标，核心验收用户亲验）
- [ ] 止损线已设定（金额 + 时间 + 触发后动作）
- [ ] 先查后造已完成（查过什么、为什么不用现成）
- [ ] 数据资产盘点表完成 + 获取成本评估
- [ ] 技术路线比选完成（≥2 候选、用户拍板、决策记录留档）
- [ ] PoC 最小验证完成（最险点明确、结论明确、回退路径明确）
- [ ] 规模预判完成（拆分组装法启用与否已判定）
- [ ] 合规风险已评估（数据隐私、版权、行业监管）
- [ ] PRD 定稿（F 编号、不做的范围、验收标准、变更记录表）
- [ ] 契约骨架 + 评测基线冻结（变更须走变更单）
